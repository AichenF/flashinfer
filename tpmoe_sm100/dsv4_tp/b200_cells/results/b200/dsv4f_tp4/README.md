## Optimizations

Kept on this cell (all bitwise: ours2_vs_ours 0 mismatches on every rank, 2 agreeing reps, real trace):
- IDV (M >= 49): routing ids loaded as int4 vectors, all in flight before the tables' clear phase: M128..512 -0.5..-3.2 us (commit 66e06d7).
- LLS (all M): all-reduce messages = 8 bf16 per 16 B with a sentinel word (reader re-arms the slot) instead of 6 bf16 + epoch tag:
  -25% NVLink bytes; M256 / 384 / 512 -1.2..-2.0 / -5.1..-6.3 / -4.8..-5.5 us, small M neutral (commit 06136eb).
- XRLX (M > 128): warp 6's 16 x-flag ld.acquire before the tables were serialized (~0.3 us each) and held the clear barrier;
  relaxed loads + one fence at the check: M256 / 384 / 512 -1.4..-0.6 / -1.4..-1.8 / -2.9..-2.7 us (commit 88f4b3d).
- Guards (no effect on these builds): lls_allreduce traps if gridDim != TPB2_GRID (c54caf3); static_assert(!TPB2_SFBI || TPB2_WHOLE)
  -- the SFBI per-item SFB image double buffer is written before the piece's first EMPTY wait and is only safe when the previous FC1
  piece has >= NS stages, which whole items (TPB2_WHOLE=1, every shipped / suite build) guarantee.  Race stress (stress_v77.py,
  results/b200/_stress): production SPEC=1 builds at 39 M values and these routed builds at M256 / 384 / 512, up to 160k back-to-back
  calls per M (eager + graph), 0 mismatches.
- v4ft at M >= 384 (6a01f29): same-run vs v77, 2 swapped reps, TP4 M384 / 512 -4.1..-4.8 / -12.8..-13.0 us (TP8 -0.7..-2.0 / -4.1..-4.8);
  v77 stays at M <= 256 (v4ft +2..3 us there).  Gate: checks + b2b 12 every M + b2b-mix (v77 <-> v4ft switching on one stream) 0
  mismatches; stress 1500 x 8 eager + graph, 2 cases, M384 / 512 single and mixed with M64: 48k calls per rank each, 0 bad
  (results/b200/_gate_v4ft).

Refuted here (A/B, kept off): IDV 2 (ids loaded before the x quant: neutral), IDV 3 (match_any-merged atomics: +1..4 us),
PFD (L2 prefetch of the first FC1 stages: +7..13 us), GATHER=0 / FC2G4_MINM / ACTX=0 / SFBI=0 / ARV=35, NMAX 24+NS5 / 32+NS4 / 64
(smem / illegal instruction), MC=2 (NVLS all-gather: ingress-bound, the v77 author's result), T1W (incompatible with LASTM / FC2VAR),
an ids hot-line theory (8 / 37 replicas of the ids: no change), ENTT (build_tables entries per token: -0.7 us in the tables at
M512 but end-to-end within +-1 us, reps disagree).

## Timing caveat

In some processes ours (v77 and tp8v41 alike) runs 5-15% slow at the larger M -- for one M or for the rest of the process -- while gc in the same process is normal (suite f8tr_1f / f8trL_1f / f8trX_1f, my c4ftrB_1f / k064 / k091 / k097_2).  It is not reproducible on demand: 4 repeated check-1 processes, fresh-build processes and pre-capture eager calls were all clean, and the post-timing graph output stays bitwise (post_mism 0), so it is a timing state, not a wrong-result mode.  The trigger is not understood.  The per-rep values are in each result.json (`*_1f` vs `*_2f` / `*_3f`); prefer the clean reps when comparing builds.  Node-to-node spread is ~4%; B200 event timestamps are quantized to ~2.05 us.
